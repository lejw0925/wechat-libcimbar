# 接收速度调查

日期：2026-10-03；当前修订：`adaptive-sampling-9`。用户反馈：相同接收模式下，小程序约比 CFC 安卓端慢 8 倍，安卓手机本身性能更弱。本修订启用自适应采样和兼容通道投递前裁剪；真实提速幅度仍需两部手机的诊断与完整文件接收时间确认。

## 本次实现

两条相机通道均从 8 fps（125ms）起步，档位为 4、8、12、20 fps。升档需要至少 8 次连续有效计时，且距离启动／上次变档至少 1.5 秒；逐级升档，不直接跳到最高档。

工作耗时取 `workerElapsedMs`、`roundTripMs`、`sampleWorkMs` 的最大值，使用 0.25 权重的指数平均。只有当前耗时不超过本档间隔的 65%、不超过下一档间隔的 80%、平均耗时不超过下一档的 75%，且实际回复间隔至少为工作耗时的 1.5 倍，才累计升档样本。连续两帧耗时达到本档间隔的 90%，或单帧达到 125%，立即降一档；恢复升档需要重新积累稳定样本。无相机帧的回复不参与调速，也不会复用上一帧耗时。

兼容路径的采样周期从开启监听开始，等待下一帧时扣除等帧、停止监听、裁剪、消息往返和解码已经用掉的时间。两条通道遇到 `busy` 均在 8ms 后重试；正常在途期间不创建下次采样计时器，收到回复后才安排下一帧，始终无帧队列。直接通道失效时重置调速估计，再回退到兼容路径。

`sampled-copy` 在停止监听后、`pushFrame` 前按原始像素密度居中裁为正方形。720×1280 的 3,686,400 字节变成 720×720 的 2,073,600 字节，跨线程像素量减少 43.75%。只保留一个尺寸精确匹配的暂存缓冲，上帧回复后复用；已有正方形帧直接使用原缓冲，暂停／停止时释放暂存引用。iOS 直连继续由 Worker 取帧并直接裁进 WASM，不增加主线程像素副本。

首次内存警告仍暂停并保留已接收数据；恢复后的本次会话固定限制在 4 fps，重新接收才恢复自适应。重复警告／Android 严重警告仍终止 Worker；单帧在途、`release-frame` 和有界文件写入保持生效。更高档位会增加单位时间的相机处理和复制量，真机需同时测内存与发热。

## 已确认的差异

| 环节 | 当前小程序 | CFC 安卓参考实现 | 对速度的影响 |
| --- | --- | --- | --- |
| 调度 | 原固定 250ms 已改为 8 fps 起步、4／8／12／20 fps 自适应，单帧在途 | 每次相机回调提交任务，原生线程池处理 | 减少有余量时的主动等待；实际帧率仍受取帧与计算耗时限制 |
| 执行 | 一个 Worker 内单线程 WASM，OpenCV 单线程 | 原生 C++，线程数为 `max(hardware_concurrency / 2, 1)`，有界线程池 | 较弱的手机也可能靠原生执行与并行更快 |
| 相机数据 | iOS 优先 Worker 直接取帧；回退路径先裁正方形再复制 RGBA，并启停监听 | 原生 OpenCV Mat 经 JNI 进入 C++，克隆后交给线程池 | 兼容路径减少了复制字节数，仍受监听启停和相机回调延迟影响 |
| 构建 | `MinSizeRel`（`-Os`）与链接 `-Oz`，未启用 SIMD 或线程 | Android 构建为 `Release` | 当前 WASM 优先缩小包体，速度编译选项值得另做 A/B |
| 画质 | 用户设备回调 720×1280，中央 720×720 解码 | CFC 会尝试选择短边 960–1080 的支持尺寸，失败则回退 | 不同清晰度、对焦和码图占比会改变单帧有效载荷，帧率不是唯一因素 |

参考 CFC 提交 `e143ebd16154f3db17fbfdf8d0da71b1b50678a4`：[多线程解码器](https://github.com/sz3/cfc/blob/e143ebd16154f3db17fbfdf8d0da71b1b50678a4/app/src/cpp/cfc-cpp/MultiThreadedDecoder.h)、[JNI 数据路径](https://github.com/sz3/cfc/blob/e143ebd16154f3db17fbfdf8d0da71b1b50678a4/app/src/cpp/cfc-cpp/jni.cpp)、[相机尺寸选择](https://github.com/sz3/cfc/blob/e143ebd16154f3db17fbfdf8d0da71b1b50678a4/app/src/main/java/org/cimbar/camerafilecopy/OpencvCameraView.java)、[构建配置](https://github.com/sz3/cfc/blob/e143ebd16154f3db17fbfdf8d0da71b1b50678a4/app/build.gradle)。

旧版正常解码后已扣除解码时间，但忙碌分支会等待一个完整间隔，相机等帧也在原周期之外。本次同时修正这两处调度，并用稳定样本决定目标档位；目标 FPS 与实测 FPS 分别记录。

## 本地可重复基准

新增 `npm run bench:decoder`，需要已经构建测试编码器、检出上游 samples，并安装 FFmpeg。它加载小程序正在使用的真实 WASM，不替换发布产物。输入转换／生成和初始化在计时外，测量包含 RGBA 裁剪复制、原生定位／解码、读取结果；大文件最后一帧包含恢复与解压。每次只保留当前帧。

环境：Apple M4、macOS arm64、Node v22.23.2。WASM SHA-256：`13d23899b3e26288ab462b28fac861efaefbc409cf7cff88e0e2b8438d3670f4`。以下是一轮测量，未测手机、微信 Worker、相机交付、显示刷新或热降频。

| 输入 | 帧数 | 平均每帧 | P50 | P95 | 原生调用平均 | JS 裁剪及结果读取平均 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 上游 B 样本，合成 720×1280 → 720×720；10 次预热后统计 | 80 | 29.12ms | 26.71ms | 41.96ms | 29.05ms | 0.07ms |
| 1 MiB 伪随机文件，B 模式，1024×1024 连续不同码图 | 145 | 31.34ms | 31.05ms | 34.78ms | 31.20ms | 0.15ms |

1 MiB 文件恢复后的 SHA-256 与输入相同，两组 WASM 堆均为 32 MiB。桌面 JS 裁剪占比很小，但这**不包含微信的跨线程复制**，也不是微信进程总内存测量。

这轮计算量对应约 32–34 帧/秒的桌面计算上限，测量时小程序尚固定为 4 帧/秒。以上表格是 Worker 内裁剪的历史计算基准，不含本次增加的主线程暂存复制。本次自适应最高档为 20 fps；目标档位不等于手机实际帧率或传输速度。基准脚本分别列出各固定档位的 CPU 算术上限，避免把启动档位当作整个会话的上限。

## 回归与后续验证

本地通过自适应升降档、缺帧、忙碌重试、两条通道的单帧限制、主线程逐像素裁剪及内存警告恢复测试。真实 WASM 验证投递前裁剪和消息克隆后的样本哈希一致，五种模式及真实拍摄样本回归通过。

`test:memory` 额外覆盖 1080×1920 投递前裁为 1080×1080、逐帧克隆消息的 1 MiB 传输：565 次解码，约 15% 时释放相机缓冲后继续，最终哈希一致，WASM 堆保持 32 MiB，主线程裁剪缓冲总共只在启动和暂停恢复后各分配一次。另两组原 Worker 裁剪测试也通过。这证明桌面缓冲复用和解码正确性，不能代替微信进程总内存测量。

真机下一步记录档位变化、整文件接收时间、微信峰值内存和发热；此前的 iPhone 1 MiB 内存退出仍需回归。后续可独立比较 `-O2/-O3` 与当前 `-Os/-Oz`，但本次没有修改或重建 WASM。若相同帧率下有效数据仍少，再检查对焦、画面尺寸与完整角标。

## 真机诊断与对比口径

| 字段 | 含义 |
| --- | --- |
| `targetFps` / `targetFrameIntervalMs` | 当前目标档位／间隔，初始 8 fps／125ms，可升至 20 fps／50ms；暂停快照保留暂停前档位 |
| `frameIntervalMs` | 最近两次有尺寸指标的解码回复之间的时间；暂停／恢复后重新建立基线，不是整个会话平均 FPS |
| `workerElapsedMs` | Worker 内取帧（直接通道）、裁剪、解码与生成结果的总耗时；不是纯 C++ 耗时 |
| `roundTripMs` | 主线程发出解码请求至收到结果的耗时，包含消息传递、调度及 Worker 工作；不含发请求前的相机启停／等帧 |
| `cameraWaitMs` | 兼容路径从开启监听到收到画面的等帧时间；直连为 0，其取帧成本包含在 Worker 耗时中 |
| `sampleWorkMs` / `samplingWorkMs` | 最近一次取到画面／发起直连请求至结果处理结束的耗时，以及用于调速的工作耗时指数平均 |
| `samplingChanges` / `samplingMaxFps` | 当前相机来源实例的变档次数／最高允许档位；内存警告后最高为 4 |
| `busyRetries` | 因在途请求而进行的短延迟重试次数，不产生像素队列 |
| `width/height` / `decodeWidth/decodeHeight` | 原始相机尺寸／实际解码尺寸；投递前裁剪后仍保留原尺寸 |
| `inputBytes` / `postBytes` | 原始 RGBA 字节数／本次跨线程投递的相机像素字节数；iOS 直连 `postBytes` 为 0 |
| `cropMs` / `cropBufferBytes` | 最近一帧主线程裁剪耗时／暂存缓冲容量；直连均为 0，暂停会释放该缓冲，历史帧指标保留 |
| `transport` | `ios-worker-camera` 或 `sampled-copy` |
| `receiveBytesPerSecond` | 去重后的 fountain 有效载荷速度，包括不同修复包，排除相机像素与重复包 |
| `heapBytes` / `peakHeapBytes` | WASM 线性内存，不代表整个微信进程内存 |

诊断只追加少量数字，不保存像素或新增日志数组；保留两份快照和 5 秒写入节流。毫秒计时受系统时钟精度影响，应看连续多个采样，不能用单次差值精确衡量复制成本。未收到可解码帧时，相应耗时字段可能尚不存在。

对比时固定发送端、文件、模式、播放 FPS、屏幕亮度和码图尺寸，记录从有效数据开始至解码完成的总时间，分开记录本地保存时间；同一文件至少接收三次、校验 SHA-256。iPhone 小程序与另一台安卓 CFC 的结果只能作为实际体验对比，不能完全分离硬件与运行环境的贡献。有条件时再在同一安卓手机比较 CFC 与小程序。不能直接拿两个产品显示的速度数字相除而忽略计数口径。
