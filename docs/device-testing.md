# Android / iPhone 真机验收

两端均需记录手机型号、系统版本、微信版本、基础库版本、代码包版本。请使用真实 AppID 预览，先验证几十 KiB 文件，再测试较大的文件。测试结果需要在手机上实际记录，不能用桌面 WASM 测试代替。

> 验收进度（2026-10-04）：iPhone 与 Android 基础接收与本地保存已实测通过（iPhone 有效速度 86.4 KiB/s，3.4 MiB 多次完整接收；Android 约 50 KB/s），小程序已正式上线；原生鸿蒙（HarmonyOS NEXT）尚未测试。其余单项仍以下文实际记录为准。

## 基础接收

1. Android 和 iPhone 分别启动小程序，应直接显示扫码页。首次启动检查隐私与相机授权弹窗，不再经过准备页或要求先点开始按钮。
2. 拒绝权限，确认界面有明确错误和“打开权限设置”；重新授权后可重试。
3. 从 cimbar.org 发送一个已知 SHA-256 的文件，双方设为 B。码图四角完整入镜，接收完成后核对文件大小。
4. 输入中文文件名并保留扩展名，确认保存；退出小程序，再上滑扫码页底部“历史接收”，确认记录与内容仍存在，旧版本保存的文件也应直接可见。
5. 使用“导出文件”转到自己的文件传输助手，下载导出的文件到电脑，核对 SHA-256。
6. 左上角“更多”中滑块选择 Mini / Micro / 旧版 4 色 / 旧版 8 色，使用匹配发送端分别测试；模式不一致时不应显示虚假成功。

## 扫码首页、深色模式与历史面板（history-motion-8）

1. 首页左上角“更多”、中间“扫码”位于胶囊所在的顶部导航区域，右侧不再有历史按钮，下面不应再有第二行导航。应用按钮不应覆盖微信胶囊、状态栏或刘海。短屏手机主操作应位于折叠历史面板上方，取景始终正方形，没有横向溢出。较大系统字体下单独检查换行和点击区域。
2. 更多和许可使用微信原生标题和返回按钮。更多列表外边距 16px、行内留白 16px，列表按钮铺满分组；主要文本统一 17px，辅助说明、档位、网址及开源操作文字统一 13px。滚动更多时渐变背景固定在视口，诊断分组只保留复制入口，尺寸数据仍包含在复制结果中。历史通栏面板内留白 24px，文件呈普通列表行。页面和抽屉均无模糊滤镜，分组和抽屉为实色。
3. 分别以浅色／深色启动，检查扫码、历史、命名输入框、更多滑块、开源区和许可页。使用微信跟随系统设置后，在小程序打开时切换外观，原生状态栏／导航与正文颜色应同步变化；深色无白色底部闪块或白底黑字输入框。更多页反复进入退出不会累积主题监听。
4. 历史平时仅显示标题、文件数及渐变预览，无文字模糊。分别从标题和预览区域慢慢向上拖，面板全程跟随手指；中途松手按距离吸附，快速轻扫可展开／收起。上限停在导航下方，不遮胶囊。重新抓住正在吸附的面板，不应跳到终点，也不能因上次动画通知而突然暂停或恢复相机。标题点按仍能展开／收起。
5. 分别从标题、列表顶部的文件行、内容空白和空列表中向下拖，均能收起；滑动抽屉时下方扫码页保持不动。长列表独立滚动、末行完全露出，向下滚到列表顶部后可接续拖动抽屉，不能跳动或误打开文件。分别测试长中文名、待命名标记、取消手势、第二根手指加入、横竖屏变化和底部手势区域；取消后不能卡在半展开。输入文件名时检查软键盘与面板避让。
6. 接收约 15% 时上滑历史，拖动和松手吸附期间相机继续运行，完全展开后才暂停且保留进度；轻拉后收回不应出现暂停／重新启动。收起动画结束后自动继续同一文件。先手动暂停再展开／收起，则保持暂停。历史展开期间切后台、收到内存警告或最后一帧完成解码，收起不得误启动相机。首次授权附近展开历史，晚到授权不能在面板后挂载相机。取景框上方两个装饰角不再显示；手动暂停时应有居中的暂停图标和区别于页面的底色。
7. 更多中拖动滑块到五个档位，或点击标签。名称随档位更新，松手吸附；标准、Mini、Micro、4 色、8 色分别对应模式 68、67、66、4、8。退出重开记住最后选择。GitHub / Star 保留在更多中，说明默认折叠，不启动额外相机或 Worker。
8. 接收中打开更多仍暂停并保留进度，返回后需点“继续接收”。有进度时更换模式，返回扫码页应询问；取消保留旧模式／进度，确认才释放旧 Worker、清空进度并用新模式接收。未收到数据时可直接使用新模式。
9. 已完成但尚未命名、保存后或写入失败可重试时修改模式，不得丢弃当前文件；新模式用于下一次接收。写入／保存过程中更多和历史文件操作暂时禁用；如果最后一帧在历史展开时完成，仍可收起面板查看命名结果。
10. 点按历史文件行，测试命名、预览、导出、取消操作和删除确认。命名或删除当前结果后收起面板，扫码页同步状态，不能显示失效文件名。取消命名不得清空扫码页已有的输入；完整待命名记录可恢复和导出，重复点按不能并行修改文件。
11. 重新打开后自动扫码，不应覆盖上次异常诊断。更多中分别复制本次和上次记录，确认时间、模式及进度对应正确，且本机只保留两份快照。

## 暂停、退出与重试

- 接收中点击暂停，再继续；进度保留。切后台、锁屏或查看更多后返回仍为暂停，不应自动重置或自动恢复相机。历史展开／收起只恢复展开前正在进行且未被其他事件暂停的接收。关闭进程后未完成的传输需要重来。
- 暂停后点击重新接收，确认后进度清空；保存后点击“继续扫码”，发送第二个文件应能完成。
- 刚解码完成但尚未命名时退出，在文件列表找到“待命名”记录并完成命名。
- 在写入过程中终止进程，确认半文件不会显示为接收成功。此时尚未完整落盘的数据需重新接收。
- 拒绝相册权限、取消转发、目标文件不支持预览时，确认本地文件仍保留。
- 重复接收相同文件，命名冲突时生成“文件 (2).扩展名”，不覆盖先前内容。
- 确认删除只删除所选记录。该操作不可恢复。

## 画质与性能

记录 100 KiB、1 MiB、5 MiB 文件的接收时间、丢帧表现、发热和后台恢复结果。分别测试轻微倾斜、距离变化、屏幕反光。当前 8 fps 起步，在 4／8／12／20 fps 间自适应，同时仅一帧在解码；目标档位不等于实测帧率。相机回调分辨率由微信决定，不一定与预览分辨率相同。iPhone 优先 Worker 直接取帧，Android 和兼容路径按单帧启动／停止监听，裁为正方形后才投递。

首版不含镜头畸变标定或自动模式识别。较强透视、广角镜头畸变、低像素帧及频繁对焦可能降低成功率；先调整距离和发送模式，再记录具体机型问题。

与 CFC 安卓版对比时固定同一个文件、模式、发送 FPS、屏幕亮度和码图尺寸，分别记录完整接收时间，至少重复三次。`targetFps` 初始 8、`targetFrameIntervalMs` 初始 125；`frameIntervalMs` 是最近两次回复间隔；`workerElapsedMs` 是 Worker 内耗时；`roundTripMs` 是主线程请求往返，不包含发请求前等帧和主线程裁剪，分别看 `cameraWaitMs` 与 `cropMs`。暂停后应重新建立帧间隔基线，不能混入长时间暂停。记录微信总内存，不能只看 WASM 堆。字段与升降档条件见 [performance.md](performance.md)。

## 自适应采样与投递前裁剪（adaptive-sampling-9）

1. 在 iPhone 直连和 Android／兼容路径分别测试。持续低耗时时，目标档位应按 8 → 12 → 20 逐级变化；每次升档至少间隔 1.5 秒，不应在 12／20 间频繁抖动。实际回复间隔可高于目标间隔，尤其是取帧慢时。
2. 观察透视校正较重、设备发热或负载升高时的 `workerElapsedMs`、`roundTripMs`、`sampleWorkMs`，接近当前间隔应降档；恢复后须有一段稳定余量才再次升档。重复／缺失相机帧不应造成虚假的速度或沿用旧耗时升档。
3. 兼容路径原始 720×1280 时，诊断仍为 `width:720,height:1280`，解码 720×720，`inputBytes:3686400,postBytes:2073600`。直连 `postBytes`、`cropMs`、`cropBufferBytes` 均为 0。横竖屏切换后核对实际尺寸、裁剪范围和完整文件哈希。
4. 接收中快速暂停／继续、展开／收起历史、切后台、原生相机暂时无帧或直连回退，确认没有堆积帧或停止后的复活计时器。`busyRetries` 可增加，但不会因此等一个完整 125／83／50ms 间隔。
5. 首次内存警告后仍暂停并保留进度；继续接收时 `samplingMaxFps`、`targetFps` 应为 4，本次会话不再升档。再次警告仍终止 Worker。对原来退出的 1 MiB 文件至少完整接收三次，分别记录微信进程峰值内存、发热及接收时间。

## 正方形画面与实时速度（square-speed-3）

1. 检查取景区域为正方形，完整码图四个角标均在框内。在“更多 → 复制本次接收诊断”读取真实尺寸字段：720×1280 的原始帧应对应 720×720 解码，1080×1920 对应 1080×1080。更改预览宽高不代表原始分辨率提高。
2. 转动手机或切后台恢复后检查显示尺寸及取景范围；确认四角没有被中央裁剪区域截掉。若预览与实际视野不一致，记录机型和两个尺寸供排查。
3. 收到有效帧后速度应以 KiB/s 等单位显示。遮住码图或持续显示同一帧，约 3 秒后应回落到零；不能把重复帧算成新的文件数据。
4. 暂停时显示“已暂停”；继续后重新计算短时速度，不应把暂停时长算进分母，也不应产生积压数据的假峰值。
5. 完成、退出或收到内存警告后，速度刷新计时器应停止，不产生后台持续刷新。
6. 更多底部的源码／Star 入口应复制公开仓库链接，并提示在浏览器打开；取消或复制失败不应声称已经 Star。

## iPhone 1 MB 内存退出回归（含 memory-2 修复）

已知旧版表现：十几 KiB 文件可成功；约 1 MB 文件在接收进度约 15% 时退出，提示内存占用过多。不是解码完成后的保存阶段。以下步骤用于复测，不能以本地测试通过代替。

1. 开发者工具重新编译并生成新的预览二维码，手机打开新版。无需重建 WASM，也无需清理小程序数据（清理会丢失已保存文件）。
2. 用原来的同一个 1 MB 文件、相同模式测试；建议发送速度先设为 4～6 帧/秒。完整接收、重命名保存，再导出核对 SHA-256。
3. 打开更多，点击“复制本次接收诊断”，确认 `revision` 为 `adaptive-sampling-9`。记录 `transport`：支持的 iPhone 应为 `ios-worker-camera`；`sampled-copy` 表示兼容采样路径，并非接收失败。`width/height` 是相机尺寸，`decodeWidth/decodeHeight` 是裁剪后的实际解码尺寸。
4. 在约 15% 处手动暂停／恢复一次，确认进度不清空。接收过程中切后台再返回也需测试；重复接收同一文件至少三次。
5. 若收到系统内存警告，首次应自动暂停并保留进度。稍候继续；若再次警告则终止会话并提示重新接收，已保存文件不受影响。加载阶段或 Android 严重警告直接释放线程。
6. 若再次退出，重新打开后直接去**更多 → 复制上次接收诊断**，不要先反复重试。自动扫码会备份上一会话；将上次诊断和当时现象提供给开发者。当前快照每 5 秒保存一次，可能略早于退出瞬间；若系统未发警告，`memoryWarnings` 也可能为 0。

诊断中的 `heapBytes` / `peakHeapBytes` 仅为 WASM 线性内存，不是微信进程总内存。桌面 `npm run test:memory` 的三组 1 MiB 长时间测试（含投递前裁剪及消息克隆）保持 32 MiB；新增路径暂存缓冲仅启动和暂停恢复后各分配一次。真实相机和微信跨线程缓冲仍须在手机上观察。诊断仅保留本次和上次两份本机快照，不记录像素、文件内容或文件名，不自动上传。

## 开发者工具自动化

已用工具随附的 `wcc`、`wcsc` 通过 WXML、WXS 手势代码和样式编译。完整模拟器自动化需要在开发者工具的“设置 → 安全设置”开启服务端口；本次没有修改这一设置。模拟器适合检查页面、文件列表及错误提示，相机和手机文件出口仍需要上述真机测试。

`history-motion-8` 另做了编译后 WXML 的浏览器检查，注入微信 v2 按钮默认宽度／边距规则。18 组布局覆盖浅色／深色的 320px / 390px 扫码、暂停状态、历史折叠／半展开／展开／空列表、更多、命名和许可页。检查横向溢出、点击区域、对齐、导航避让、方形取景、主操作不被折叠面板覆盖及无模糊滤镜。触摸事件运行真实手势代码，验证面板移动 140px、相机状态通知晚于吸附动画、内容区下拉收起且底层滚动为零、长列表独立滚动；更多背景在页面滚动时保持固定，主要文字均为 17px。另有 85 项 Node 测试覆盖接收、文件和手势状态。

当前 `adaptive-sampling-9` 的 97 项 Node 测试、真实 WASM 回归及三组 1 MiB 内存回归通过。本次未改 WXML／WXSS，前述界面检查属于 `history-motion-8` 的验证结果。

此检查使用静态数据和相机／系统区域占位，不代表微信真机画面。WXS 与微信原生滚动组件、相机和固定导航的配合仍需双端确认。
